# Indexing Strategy

**Version:** 1.0
**Status:** Draft
**Location:** `/docs/06-data-architecture/07-indexing-strategy.md`

---

# 1. Purpose

This document defines the indexing strategy for the MaintainPro platform.

Indexes exist to improve query performance while maintaining data integrity and predictable system behavior.

Poor indexing leads to:

* slow queries
* increased CPU usage
* excessive disk reads
* degraded scalability

Every collection should be indexed deliberately.

---

# 2. Philosophy

Indexes are created to support real business queries—not hypothetical ones.

MaintainPro follows:

* query-driven indexing
* minimal index duplication
* predictable performance
* measurable optimization

Every index should have a clear purpose.

---

# 3. Indexing Objectives

Indexes should optimize:

* lookups
* filtering
* sorting
* uniqueness
* tenant isolation
* reporting

Indexes should never exist without an identified workload.

---

# 4. Primary Index

MongoDB automatically creates:

```text id="x3h2tm"
_id
```

Every document is uniquely identifiable through this index.

---

# 5. Tenant Indexing

Every tenant-owned collection should include an index on:

```text id="v0lw6d"
organizationId
```

Since nearly every query is tenant-scoped, tenant filtering must remain highly efficient.

---

# 6. Compound Indexes

Compound indexes support common business queries.

Example:

```text id="r5nk8u"
organizationId

↓

status

↓

priority
```

Supports queries such as:

> "Show all active high-priority work orders for Organization A."

Column order should follow query selectivity.

---

# 7. Unique Indexes

Business identifiers requiring uniqueness should use unique indexes.

Examples:

```text id="1jv8yr"
organizationId + assetNumber

organizationId + workOrderNumber

organizationId + vendorCode
```

Uniqueness is typically scoped to an organization rather than the entire platform.

---

# 8. Foreign Reference Indexes

Frequently joined references should be indexed.

Examples:

```text id="g2m7pa"
organizationId

vendorId

assetId

assignedUserId

locationId
```

Referenced lookups should remain efficient.

---

# 9. Sorting Indexes

Frequently sorted fields should be indexed.

Examples:

```text id="5kc4wl"
createdAt

updatedAt

scheduledDate

dueDate

completedAt
```

Indexes should support both filtering and sorting where appropriate.

---

# 10. Search Indexes

Fields commonly searched by users should receive indexes.

Examples:

```text id="e8r5tw"
assetName

vendorName

serialNumber

email

phoneNumber
```

Full-text search should use dedicated search capabilities where appropriate.

---

# 11. Partial Indexes

Indexes should avoid inactive records when appropriate.

Example:

```text id="w4py7n"
deletedAt = null
```

Partial indexes reduce storage and improve lookup efficiency.

---

# 12. Sparse Indexes

Sparse indexes should be used only when optional fields are frequently queried.

Example:

```text id="n7ld0s"
imeiNumber

(optional)
```

Sparse indexes should not replace proper schema design.

---

# 13. TTL Indexes

Temporary collections may use TTL (Time-To-Live) indexes.

Examples:

* login sessions
* password reset tokens
* email verification tokens
* temporary exports

Permanent business entities should never use TTL indexes.

---

# 14. Index Naming

Indexes should use descriptive names.

Example:

```text id="4sq1dx"
organization_status_priority_idx
```

Avoid autogenerated or ambiguous index names in production deployments.

---

# 15. Write Performance

Indexes improve reads but increase write cost.

Before adding an index, evaluate:

* query frequency
* update frequency
* storage overhead
* maintenance cost

Unused indexes should be removed.

---

# 16. Monitoring

Index effectiveness should be monitored using:

* query execution plans
* index usage statistics
* slow query logs
* collection scans

Indexes should be reviewed periodically.

---

# 17. Repository Responsibility

Repositories should use queries aligned with defined indexes.

Repository implementations should avoid query patterns that bypass indexed fields.

---

# 18. Architectural Rules

* Every tenant collection indexes organizationId.
* Business identifiers use unique indexes.
* Compound indexes match business queries.
* Foreign references are indexed.
* Sorting fields are indexed when frequently used.
* Temporary data may use TTL indexes.
* Indexes are continuously reviewed.

---

# 19. Anti-Patterns

Avoid:

* indexing every field
* duplicate indexes
* unused indexes
* relying on collection scans
* unique indexes on mutable business fields without justification
* indexing low-selectivity fields unnecessarily

---

# 20. Future Enhancements

The indexing strategy should evolve to support:

* Atlas Search indexes
* vector indexes for AI features
* sharded cluster index optimization
* automated index recommendations
* workload-aware adaptive indexing

---

# 21. Guiding Principle

> **MaintainPro creates indexes based on actual business access patterns rather than assumptions. Every index serves a measurable purpose, balances read performance against write cost, and supports secure, tenant-aware, and scalable data access across the platform.**
